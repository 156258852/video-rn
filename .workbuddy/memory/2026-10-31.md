## iOS「一个播放器」方案调研（未改代码，仅结论）

问题：能否不用 RN 双播放器拼接，改在 iOS 原生侧用 playlist / 单个播放器。

结论：
- AVQueuePlayer 不适合本项目：播完的 item 会出队无法回拖；currentTime / duration 只覆盖当前 item，全局时间轴仍要自己算。
- 正解是 AVMutableComposition：把 N 个 clip 拼成一个 asset，AVPlayer 只看到一条连续时间轴，seek / duration / onProgress 天然全局，可回拖。

关键落地钩子（react-native-video 6.19.2，无需 fork 库）：
- `node_modules/react-native-video/ios/Video/RNVAVPlayerPlugin.swift:47` `overridePlayerAsset(source:asset:) async -> OverridePlayerAssetResult?`
- `ios/Video/ReactNativeVideoManager.swift:39` `registerPlugin(plugin:)`
- `ios/Video/RCTVideo.swift:542-545`：返回 `.full` 时直接 `AVPlayerItem(asset:)`，跳过默认 prepare 流程

传参限制：JS 层 `src/Video.tsx:281-304` 的 `sourceToUnternalSource` 只透传白名单字段，自定义字段会被丢弃 → playlist 只能塞进 uri（如 fragment）或另写 bridge 模块。

已知坑：三个测试片分辨率不同，需 AVMutableVideoComposition 统一 renderSize，但插件只能返回 asset、拿不到 AVPlayerItem，需在 `onInstanceCreated(id:player:)` 里 KVO `currentItem` 后再设 `item.videoComposition`；`load(.duration)` 是 iOS 15+ API。

## 相关既有结论

- 播放引擎层本就是原生 AVPlayer（`ios/Video/RCTVideo.swift:1244` setControls：`controls=true` → AVPlayerViewController，`false` → AVPlayerLayer）。
- 当前 RN 侧自绘 UI（App.tsx:201 `controls={false}`、Modal 全屏 App.tsx:445、自绘 scrubber），与虚拟拼接耦合；若改原生控件会破坏 useVirtualTimeline / watchedSeconds 统计。

## Swift 6 / Xcode 27 的两个编译坑（已修）

1. **`NSLog` 在 Swift 里不可用**：`error: 'NSLog' is unavailable: Variadic function is unavailable`。Swift 6 不允许调用 C 可变参数函数。改用 `import os` + `Logger(subsystem:category:)`（iOS 15+），字符串插值要标 `privacy: .public`，否则 log stream 里显示成 `<private>`。OC 文件（AppDelegate.mm）里的 NSLog 不受影响，可保留。
   代价：`Logger` 是 iOS 15.0+，若将来要支持 iOS 14 及以下需换回 `print()` 或加 `#available` 判断。
2. **`static` 成员在实例方法里必须加 `Self.`**：`error: static member 'cache' cannot be used on instance of type`。如 `await cache.store(...)` → `await Self.cache.store(...)`。

另：把 `xcodebuild ... | grep ... && 后续安装命令` 这种写法废弃 —— 管道后 `&&` 判断的是 **grep** 的退出码，grep 无匹配即返回 1 会静默断链，导致编译失败时仍拿旧的空壳 `.app` 去安装（报 `StitchRNPOCModern.app is missing its bundle executable`）。正确做法是 `xcodebuild ... > /tmp/rnbuild.log 2>&1 && ...`，日志单独 grep。

## Android 端同样可行，且比 iOS 简单（源码已确认）

react-native-video 6.19.2 **Android 端也有插件机制**，底层是 **Media3 (ExoPlayer) 1.8.0**（`android/gradle.properties: RNVideo_media3Version=1.8.0`, minSdk 24）：

- `android/src/main/java/com/brentvatne/exoplayer/RNVExoplayerPlugin.kt:49` `overrideMediaSourceFactory(source, mediaSourceFactory, mediaDataSourceFactory): MediaSource.Factory?`
- 同文件 `:59` `overrideMediaItemBuilder(source, mediaItemBuilder): MediaItem.Builder?`
- `com/brentvatne/react/ReactNativeVideoManager.kt:103-111` 遍历插件，返回 null 继续下一个（与 iOS 一样的守卫语义）；`:56` `registerPlugin(plugin)`
- `ReactExoplayerView.java:1132-1152` override 后的 factory 用于 `createMediaSource(mediaItem)`，其返回值再交给 player

**关键差异（比 iOS 舒服的地方）**：
1. `com/brentvatne/common/api/Source.kt:26` `var uri: Uri?` 是 **public**（iOS 的 `VideoSource` 成员是 internal，只能从 AVURLAsset 反解）→ Android 插件可直接读 `source.uri`，含 fragment。
2. ExoPlayer **原生支持多窗口 timeline**：`player.setMediaItems(list)` 或插件返回 `ConcatenatingMediaSource` 即可。`player.duration` = 总时长、`currentPosition` = 全局位置、**`currentMediaItemIndex` = 当前第几段**（分段埋点直接可用，不用像 iOS 那样自己算边界前缀和）、`onMediaItemTransition` 给段切换事件、回拖天然支持（不像 AVQueuePlayer 会出队）。
3. 不需要预加载每个 asset 的时长（timeline 由 ExoPlayer 异步构建），iOS 的 composition 必须 await 每段 duration。
4. Android 端 `bufferConfig` 缓存仍有效（RNVSimpleCache），iOS 的 composition 下失效。

若用公司自研 bridge 封装播放器（用户公司的做法），最省事的就是 `player.setMediaItems(urls.map{MediaItem.fromUri(it)})`，一行搞定。

## 分段埋点方案（composition 下如何按段统计）

需求：每一段视频要单独埋点（进入/离开/完成、每段观看时长）。

核心结论：**原生不用改**。composition 只有一条时间轴，"第几段"由 JS 侧用**每段时长的前缀和**算出边界数组 `segments: [{index,start,end,duration}]`，再由 `currentTime` 反算段号与段内秒数（二分或线性查找即可）。

唯一缺的是**每段时长**，三个来源：
- A. 复用 `hooks/useVideoDurations.tsx`（零原生改动，有模块级 `durationCache` 跨 remount；代价是要渲染 N 个 1x1 隐藏 `<Video>` 发 N 次元数据请求）。**POC 首选**。
- B. 原生合成时回传（插件合成时已 await 过每段精确 duration），需要加轻量 bridge getter 或 timed metadata。最准、零额外请求，但要写原生模块。
- C. 业务接口下发 duration（真实业务视频列表通常带时长）。最省。

统计口径建议用**区间并集**而非累加秒数：每段维护 `covered: [from,to][]`，merge 后求长度。这样回拖重看不重复计数、seek 跳过不计入，完成度 = 覆盖长度 / 段时长。旧代码 `watchedSecondsRef` 的累加方式是粗糙版。

坑：seek 造成的跨段要与自然播放跨段区分 —— 自然跨段旧段结算到段尾，seek 跨段旧段只结算到离开点，否则会把没看的部分算成已看。

## 预加载：composition 前后对比（已给结论 + 已加 prop）

旧的「预加载下一段」是什么（源码确认）：`hooks/useVideoSequencePlayer.ts:1110-1136`，在 `phase === 'ready'` 时把 `nextIdx` 的 uri 塞进 inactive slot（`PRELOAD_SLOT`），渲染第二个 `<Video paused>` 藏在下面，让它提前把下一段的元数据+数据缓冲好。切段时 `endHitGuard`（:387-397）查 `slotLoadedKey` 是否匹配：命中=直接换 activeSlot（无缝），未命中=`endMissPatch` → isLoading（黑屏）。代价是两个 AVPlayer 实例 + 两个 AVPlayerLayer 叠加。

composition 下变成三层：
1. **切段等待消失** —— composition 里没有「切段」事件，`onEnd` 只在整条时间轴末尾触发一次。
2. **跨段缓冲交给 AVPlayerItem 的滑动窗口** —— `preferredForwardBufferDuration`（`RCTVideoManager.m:24` 导出 → `RCTVideo.swift:968` 设到 `_playerItem.preferredForwardBufferDuration`）。对 composition 同样生效，窗口足够大时能覆盖住下一段。
3. **元数据反而是「一次性全量预加载」** —— 插件合成时对每段 `loadValuesAsynchronously(["duration"]/["tracks"])`，一次把所有段的 moov 拉下来，比旧方案「一段一段来」更前置；之后 `CompositionCache` 让全屏 remount 不再重复请求。

**重要发现：`bufferConfig` 在 iOS 端根本不存在**（只有 Android 有 `Source.kt`/`BufferConfig.kt`/`ConfigurationUtils.kt`；`src/types/video.ts:330` 标了 `// Android`）。所以旧代码 `useVideoSequencePlayer.ts:36` 的 `BUFFER_CONFIG = {cacheSizeMB: 200}` 在 iOS 上一直是被忽略的 —— 旧方案的预加载完全靠双 slot，不靠缓存配置。

已改 `App.tsx`（tsc + eslint 均通过）：
```diff
         controls={false}
+        preferredForwardBufferDuration={10}
         progressUpdateInterval={250}
```
只加这一条，不动 `automaticallyWaitsToMinimizeStalling`（默认 true 更安全：网络差时 AVPlayer 会等缓冲够了再播，对「必须看完拿积分」的场景优于频繁卡顿）。

## 「现在就是当成一个视频」—— 是的，但有三个边界要说清

1. 对 AVPlayer / RN 侧：是的，1 个 AVPlayerItem、1 个 duration、1 条时间轴，seek 全局可回拖。
2. 对数据源：底下仍是 N 个独立 `AVURLAsset`，各自发网络请求、各自解码，不是合并下载。
3. **隐患（插件 :135-138）**：某段 duration 拿不到（404 / 超时）时是 `continue` 静默跳过，总时长会悄悄变短且不报错。真要做容错得在这里改成「记下来回传 RN」或「整段失败返回 nil 走单视频兜底」。
